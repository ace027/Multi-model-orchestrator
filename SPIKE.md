# Phase 0 spike results

Claude Code 2.1.293 (spec minimum 2.1.287). Types were taken from the build's own `claude-code.d.ts`. The spike mod is in `spike/triad-spike/`. Each experiment was one headless run of `claude -p --model sonnet --plugin-dir spike/triad-spike`, using the experiment flags in `SPIKE_MODE`; see `spike/run_spike.sh`. The event logs are in `spike/logs/spike_r1..r5.jsonl`. The five runs cost $0.44 in total.

**Chosen mode: B (routed flat).** Questions 1 and 6 are both "no", so Mode A isn't possible.

| # | Question | Answer | How verified |
|---|----------|--------|--------------|
| 1 | Can a subagent spawn a subagent? | **No, not through the Agent tool.** The engine strips the Agent tool from subagents even when the agent definition lists it. A mod *can* spawn on a subagent's behalf: the subagent calls a mod-registered tool, and that tool's `tool.call` handler calls `$.agent.spawn`. | r1: `spike-coder` was defined with `tools: Bash, Read, Agent` and reported "No such tool available: Agent". r2: the coder called `mcp__triad-spike__delegate_menial`, the handler spawned `spike-helper` on Haiku, waited for its `turn.complete`, and returned its answer to the coder. |
| 2 | Does `agent.spawn` fire for nested spawns, with parent/depth? | **It fires for every spawn, including the mod's own `$.agent.spawn`, but the event doesn't say which subagent asked.** `parentAgentId` names the loop the spawn happened in. A mod spawn runs at the main level, so `parentAgentId` is absent even when a subagent's tool call caused it. `$.agent.list()` marks those agents `spawnedBy: "triad-spike"`. The mod must therefore track the tree itself: it knows the calling agent from the `tool.call`'s `agentId` and the child's id from the spawn result. Depth is computed in mod code. | r2 log: `delegate.in` has `callerAgentId` set to the coder's id, `agent.spawn.in` for the helper has no `parentAgentId`, and `agent.list` shows `spawnedBy`. |
| 3 | Does `agent.spawn` returning `{ model }` override the definition's `model`? | **Yes.** Setting `next({ ...e, model: 'sonnet' })` ran an agent defined as `model: haiku` on `claude-sonnet-5-5`. | r1 (no override) resolved to `claude-haiku-5-5`. r2 (override) resolved to `claude-sonnet-5-5`, per the spawn result, every `turn.step` model and the agent's own report. |
| 4 | Can `tool.call` post-process a real tool's result? | **Yes.** `const r = await next(e)` followed by `return { result: { ...r.result, stdout: '…' } }` replaced what the model read. Don't return `r` with its `ref`, or core uses its own messages unchanged. `r.text` holds the original output for archiving. | r2: the coder reported seeing `REWRITTEN-BY-MOD …` instead of `original-output-123`. |
| 5 | Is token usage observable per agent? | **Yes, exactly.** Each `turn.step` result carries `usage` (input, output, cache read, cache write, model) and `agentId`. Each `turn.complete` carries the summed `usage` for that agent's run. `session.measure` gives the session's USD cost. | Every run. For example, in r1 the coder's `turn.complete` usage was in 6 / out 372 / cache read 7,890 / cache write 4,213 on Haiku. |
| 6 | Does `agent.offer` know who is asking? | **No.** Its input has only `agent`, `description`, `source` and `provider`, with no `agentId`. It also only fires where the Agent tool exists, which is the main loop, because subagents don't get the Agent tool. | r1 to r5: 40 `agent.offer` rows per run, all from main-loop steps, with keys exactly `[agent, description, source, provider]`. |
| 7 | Can a hook validate or reshape a subagent's final return? | **Yes, at the parent's tool call, but not at `turn.complete`.** Returning `{ text }` from `turn.complete` didn't change the hand-back the parent read. A `tool.call` hook on `Agent` can `await next(e)`, check `r.text`, and return `{ deny: reason }` (or a rewritten result); the parent model sees the reason as a tool error. In Mode B the `delegate_menial` handler holds the return before the caller sees it, so it can validate and retry. Caveats: a background Agent call returns only a launch notice (the `agent.spawn` hook can force `background: false`), and a deny message must include the agent id, or the parent can't SendMessage it to ask for a resend. | r2 (`ret`): the parent still got the real report. r5 (`agentdeny`): the parent got `triad-spike: the subagent reply did not follow the return schema…` and tried to recover. |
| 8 | Can the mod see Haiku prompt size before sending, message a subagent mid-run, and stop or compact it? | **Size:** not exactly before sending. `turn.step` input gives `messageCount` and, via `$.session.messages({ agentId })`, the messages themselves (~chars), but the system prompt and tools aren't included. Exact size arrives in the step's `usage` after it is sent. Workable projection: the previous step's input + cache read + cache write + output, plus the new tool results' size (`r.text.length` from `tool.call`, keyed by `agentId`), plus a margin. **Message:** yes. `$.session.send({ to: { agentId } })` was delivered mid-run, and the helper acted on it. **Stop:** `$.turn.abort` can't stop a subagent; it only accepts the main loop's running turn. But a `turn.step` hook can answer a step itself without calling `next`, by yielding a text chunk and a stop chunk. The request is then never sent and the agent ends with that text as its answer. That's how the 95k stop returns `partial`. **Compact:** `$.session.compact()` compacts the main conversation only. The `session.compact` event carries `agentId` for a subagent's automatic compaction, but a mod can't start one. | r3 (`send`): the helper's report included PINEAPPLE. r3 (`abort`): `HooksError: … is not the running turn`. r4 (`synth`): the helper's 3rd request was never sent, and the parent got `status: partial …`. |
| 9 | Do cache reads/writes count toward Haiku's 100k pricing line? | **Yes, both count.** The key was billed $3.48 in total for about 18M input tokens. If both cache reads and writes count, the Haiku test plus the spike runs come to $3.41 (plus up to $0.55 for the failed first attempt at Run C), which matches. Every other hypothesis is too low even with the failed attempt fully billed: reads only at most $2.97, writes only at most $3.13, neither at most $2.14. So the 100k line is measured on input + cache read + cache write tokens. | Appendix A below. Only the key's total cost was available, not a per-run breakdown, so the result rests on the totals ruling out the other three cases. |

## Implications for the architecture (Mode B)

- Only the Opus orchestrator gets the Agent tool, and `agent.offer` hides `general-purpose`, `Explore`, `Plan` and `claude` from it. Because there's no per-caller menu, this is global, which is fine since only main can spawn.
- `triad-coder` (Sonnet) gets the registered tool `mcp__triad__delegate_menial`. Its handler calls `$.agent.spawn` (Haiku helper with tools) or `$.model.complete` (one-shot). It keeps its own tree (`caller agentId → child agentId`), enforces depth and the concurrency caps, and validates the helper's return before handing it back.
- Model enforcement uses `agent.spawn`'s `{ model }` for every spawn. Plugin agent types are namespaced (`triad:triad-coder`), so match on the suffix.
- Haiku ceiling enforcement: project each step's prompt in `turn.step`. At 80k, `$.session.send` a wrap-up note. When the projection would pass 95k, answer the step in the hook with a `status: partial` reply, so the request is never sent. Subagent compaction isn't available to the mod, so this replaces it.
- Return-schema enforcement happens in the `delegate_menial` handler (helpers) and in a `tool.call` hook on `Agent` (coders), with `background: false` forced and the agent id included in any deny.
- Result compression goes in `tool.call` post-processing.
- Per-agent and per-tier ledger: `turn.step` and `turn.complete` usage keyed by `agentId`, with the tier taken from the type map.
- Open risk: a `tool.call` handler that awaits a helper's `turn.complete` stayed within budget here (the helper ran for a few seconds). The 10-second hook budget excludes time spent in API calls and `next`, but not necessarily time waiting on another hook's promise. Phase 1 must check this with a helper that runs over 10s. If waiting counts, the handler should return a job id and use a second poll tool.
