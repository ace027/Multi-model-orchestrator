Spec pipeline. Arguments: $ARGUMENTS

Load the tools: ToolSearch with query `select:mcp__triad__spec,mcp__triad__persona_run,mcp__triad__persona_brief,mcp__triad__map`. The gather, check and assess stages are in code; research, writing and the critique's judgment are agent work. Do not read the codebase at length yourself.

1. Phase: the number given, else the current phase. Call spec action `gather` with it. If it says the phase is not in ROADMAP.md, stop. If it says the spec exists, ask (AskUserQuestion) Overwrite / Keep existing; on keep, suggest reviewing the file and stop.
2. Research (stage 2). From the summary, list the knowledge gaps per deliverable (Pattern / Technical / Domain). Resolve Pattern and Technical gaps with map action `query` when a map exists, then a triad:triad-helper with a narrow read-only brief: find the existing files and patterns each gap needs, citing paths. Only for unfamiliar technology or domain knowledge, add one or two persona_run research runs (read_only; pick the agents with persona_brief, e.g. engineering-senior-developer for architecture, design-ux-researcher for UX). Compile a research brief: Findings (topic | source | summary), Patterns to Follow, Open Questions (each Blocking or Non-blocking; Non-blocking ones need a default and the evidence that makes it safe), Recommended Approaches with decision coverage.
3. Write (stage 3). Call persona_run with agent `engineering-senior-developer` (or the phase's lead persona), read_only false, writable = the spec path, label `spec-write`, briefed with the requirements summary and the research brief to write the spec with these `##` sections in order: Overview; Requirements (table ID | Description | Priority Must/Should/Could | Acceptance Criteria, every phase requirement); Architecture with `### Key Decisions` (Decision | Choice | Rationale | Alternatives Considered); API and Type Contracts (or "None -- no API or type contract changes"); File Placement (Artifact | Path | Placement Rationale | Existing Pattern); Data and Control Flow; Compatibility Constraints; Failure Modes (Failure Mode | Expected Behavior | Verification); Acceptance Checks (Check | Command or Evidence | Required); Deliverables (one `### {name}` each with `- **Path:**`, `- **Purpose:**`, `- **Key Content:**`, `- **Dependencies:**`, `- **Estimated Size:**`, and optionally `- **Path Override:** true` with `- **Override Reason:**`); Open Questions (# | Question | Impact Blocking/Non-blocking | Default Chosen by Spec | Planning Effect); Complexity Assessment (left empty).
4. Critique (stage 4). Call spec action `check`. For 3+ requirements or real architectural choices, also persona_run `testing-qa-verification-specialist` (read_only, label `spec-critique`) with the spec text: requirement coverage and testability, weak decisions, deliverables an agent could not implement without guessing, and implicit assumptions (Assumption | Impact | Evidence | Action). Revise the spec with persona_run (same writer, writable = the spec path) to fix every check finding and the critique's points, converting high-impact weak-evidence assumptions into Blocking questions or chosen defaults, and appending `## Revision History` (# | Section | Change | Reason). Run `check` again; at most two revision rounds. A remaining REWORK is reported, not hidden.
5. Assess (stage 5). Call spec action `assess`; it writes the Complexity Assessment and returns the summary. Show it with the path, and: Next `/triad:plan {N}`. Spec action `trigger` reads `planning.spec_pipeline_default` (always / prompt / never) and returns a `proposals:` line from `planning.architecture_proposals_default`: `run` means plan step 2d runs the competing architecture proposals without asking, `offer` asks the user, `skip` records "Architecture proposals: skipped by settings". If there are Blocking open questions, say planning will halt until they are resolved and ask the user to answer them now (AskUserQuestion per question); write the answers into the spec as resolved decisions and run `check` again.
