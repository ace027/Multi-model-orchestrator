---
description: Plan a phase of a Legion-format project: decompose into wave-ordered plans, write them, critique and auto-refine
argument-hint: "[phase number] [--dry-run] [--auto] [--auto-refine] [--skip-board] [--skip-security] [--security] [--spec] [--domain=design|marketing]"
---
Plan a phase of the Triad project in `.planning/`. Phase: $ARGUMENTS (default: the phase STATE.md points to).

1. Load the tools: ToolSearch with query `select:mcp__triad__planning_status,mcp__triad__plan_write,mcp__triad__plan_check,mcp__triad__persona_brief,mcp__triad__intent,mcp__triad__dry_run`. If flags were given, call intent action `check` with command `plan`; on a validation failure show it and stop. With `--dry-run`, call `dry_run` with command `plan` (and the phase), show the report and stop: no files, agents or git changes.
   Gates: every "ask the user" below is a confirmation gate, asked with AskUserQuestion. It is skipped, taking the default it names, when `planning_status` reports confirmation gates off (control mode autonomous) or with `--auto`.
   `--auto` skips the confirmation gates below and takes their defaults (board quick-assess runs unless `--skip-board`; proposals follow the spec's recommendation, else skip; the critique runs; design review runs for design phases; the security scan runs unless `--skip-security`). It never loosens permissions. A BLOCKER (critical security finding, Blocking spec question, REWORK after the refine cap) halts the pipeline. `--auto-refine` re-plans automatically after the critique (max 2 rounds).
2. Call `planning_status` for the position. Read the phase's block in `.planning/ROADMAP.md` (goal, requirements, success criteria, recommended agents), `.planning/PROJECT.md`, and the SUMMARY.md handoffs of the previous phase. If the phase already has plan files, ask the user: re-plan from scratch, or keep them and stop (gates off: keep them and stop).
   Memory, when `.planning/memory/` exists: load `mcp__triad__memory` and call it with action `recall` on the phase's main topics (patterns, pitfalls, preferences). Read the latest entry of `.planning/memory/RETRO.md`: its High-priority action items are constraints on this plan, and "prefer {agent} for {task_type}" lines are agent-selection hints. `persona_brief` already adds agents' memory scores.
2b. Board quick-assess (offer it for phases with real architectural or product choices; with `--auto` it runs unless `--skip-board`): load `mcp__triad__board` and call action `review` with the phase. Its concerns and recommendations are planning constraints; red flags go to the user before decomposing (gates off: record them as constraints and go on).
2c. Domain: load `mcp__triad__domain` and call action `detect` with the phase (pass `flag` for `--domain=`). For a design or marketing phase, run `/triad:design` or `/triad:marketing` steps 1-5 first unless the document already exists, follow the wave pattern it returns, and reference the document (`.planning/designs/…` or `.planning/campaigns/…`) in every plan's context. If it only returns a hint, ask the user whether to use that workflow (gates off: no).
2d. Spec: load `mcp__triad__spec` and call action `trigger` (flag true with `--spec`). `run`: run `/triad:spec` for the phase first. `offer`: ask the user (gates off: skip the spec). If `.planning/specs/` has this phase's spec, call spec action `check`: Blocking open questions halt planning until the user resolves them; otherwise its deliverables, contracts, file placement, failure modes, acceptance checks and chosen defaults are planning inputs. When the spec's assessment recommends competing proposals (or the phase is complex and the user agrees; gates off: only on the spec's recommendation), run 2-3 read-only persona_run proposals (Minimal, Clean, Pragmatic philosophies; same context each), present them side by side and ask the user to choose (gates off: Pragmatic), record the choice (or "Architecture proposals: skipped by user") in the plan context.
3. Ground the plan in the code. If `.planning/CODEBASE.md` exists, use its data and the map tool (action `query`) first, and warn when map action `check` says it is stale. Then give a triad:triad-helper a narrow read-only brief to report the files, interfaces and test commands the phase touches. Do not read the codebase at length yourself.
4. Decompose the phase into plans. Each plan:
   - has at most 3 tasks (`planning.max_tasks_per_plan` in settings.json), each with exact files, decision-complete actions, `verification` shell commands that exit 0 when it is done, and a done sentence;
   - lists every file it may change in `files_modified` and what it must not touch in `files_forbidden`;
   - has plan-level `verification_commands` that prove the plan as a whole;
   - names its persona in `agents` (first one runs it; call `persona_brief` with the plan's task to choose);
   - sits in a wave: plans in the same wave run in parallel and must not share files; a plan depends only on earlier waves (`depends_on`: "NN-PP").
   Make the decisions here. Nothing may say "decide later", "TBD" or "as needed".
4b. Hybrid agent selection (gate): show a table of the plans with the recommended persona for each (from `persona_brief`, with its score and one-line reason) and ask the user with AskUserQuestion: "Accept all (Recommended)", "Change some" (then, per plan to change, offer the next ranked personas from `persona_brief` as options), or "Cancel". Put the chosen persona first in each plan's `agents`. Gates off: accept the recommendations. Never offer `agents-orchestrator`; it is never spawned.
5. Call `plan_write` with the phase, the context (goal, requirements, what earlier phases built, key decisions) and the plans (`replace: true` if the user chose to re-plan).
6. Critique. The tool returns a mechanical verdict. Also judge, yourself, what code cannot: are requirements covered, are the tasks decision-complete, will the verification commands actually prove the success criteria, is the wave order right?
7. Auto-refine: if the verdict is REWORK, or your judgment finds a real gap, fix the affected plans and call `plan_write` again with `only` set to their plan numbers. At most 2 refine rounds. Then call `plan_check` once more.
7b. With `--security` or `--auto` (not `--skip-security`): load `mcp__triad__security` and call action `scan` with the phase, then check each planned file that touches auth, crypto, input handling or API routes has security considerations in its plan; a CRITICAL finding halts. Design phases with `--auto` (or on request): run the 7-pass design review with persona_run `design-ui-designer` on the plans (information architecture, interaction state coverage, user journey and emotional arc, AI slop, design system alignment, responsive and accessibility, unresolved decisions; each 0-10, remediate plans below 7, ask the user about every unresolved decision; gates off: take the designer's recommended option and record it), then domain action `passes` with the scores and the phase. With `--auto`, show the pipeline summary table (Board Assessment, Decomposition, Plan Critique, Design Review, Security Scan: status and key findings).
8. GitHub sync (never blocks planning): load `mcp__triad__github` and call action `mode`.
   - `prompt`: ask the user with AskUserQuestion "Track this phase on GitHub?": "Yes, this time", "No", "Always" (call action `set` with `enabled`), "Never" (call action `set` with `disabled`). Gates off: "No".
   - `enabled`, Yes or Always: call action `issue` with the phase. It creates the phase issue with the plan checklist (build ticks it, review closes it). If it reports gh is not available, mention it in one line and go on.
9. Report to the user: the plans by wave (one line each), the final verdict, any remaining CAUTION items, the issue link if one was created, and the next command `/triad:build`.
